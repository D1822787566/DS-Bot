# 插件发现、兼容性检测与 Bot 预设选择开发文档

用户已确认 MVP 范围、UI 结构和主要交互，明确要求按文档开发。公开 API 核验、代码实现与测试已执行。下文历史候选以「20. 最终实现与验收」为准；未验证能力不作为完成承诺。

## 1. 目标与使用场景

用户在 DS Bot 内发现、安装 DSH 插件，看到它们提供的预设及兼容性；创建或配置 Bot 时选择预设，同时保留身份、专属指令、团队规则、工具使用规则和长期对话规则。StudyMate 是首个待验证案例，不预先宣称兼容。

## 2. 当前行为

代码核对基于本地 main；引用均为仓库相对路径。

- `ds-bot/src/host/roster.js`：`botPreset()` 优先选择有效的 `standard`；不存在时不指定预设。`createSession()` 统一应用此结果；`buildBot()` 没有预设参数。
- `ds-bot/src/host/prompt.js`：通过 `systemPrompt.section` 添加身份与团队规则，Main Bot 额外添加管理规则。权限不能只靠提示词保证。
- `ds-bot/src/host/parts.js`：换段调用 `rt.createSession()`；还使用预设提供的 compaction 服务，须检查外部预设与换段机制的关系。
- `app/src/profile.mjs`：使用独立 `ds-bot` profile，固定 bundle 在前，保留用户安装的其他 bundle。
- `ds-bot/src/client/index.js` 的 `voiceSetup`：可选使用 `pluginNavigation.openBundle()`，并明确注明桌面应用 profile 没有 plugin manager。不能假定把现有页面导航过来就能完成迁移。
- `ds-bot/dev/harness/package.json`：当前测试 DSH 为 `0.2.1-rc.5`。
- `app/test/profile.test.mjs`：已有保留用户 bundle 的测试。它不能证明第三方预设可绑定 Bot。

历史约束：`docs/plans/2026-10-13-dsh-concessions.md` 的 C1、C13 说明固定 standard 的工具兼容原因；C7、C8 记录第三方样式和工具视图的限制。改变这些设计需要维护者确认，不能把本草稿视为替代决定。

## 3. 期望行为

从发现插件、安装、检测到选择预设，用户能够在 DS Bot 界面完成；能解释哪些能力可用、哪些尚未验证。安装成功、预设可绑定、专用界面可用是不同结论。

## 6. Agent 建议

以下支持矩阵均为候选范围，须确认及验证。

| 类型 | 候选处理 |
|---|---|
| 通过公开 API 注册、有效且依赖齐全的 Agent 预设 | 可进入绑定验证 |
| 提示词、Skills、原生工具组合 | 检查必需工具与权限，验证后可绑定 |
| 自定义模型路由、上下文处理或工具调用模式 | 逐项验证；未知即待验证 |
| 自带阅读器、侧栏、工具视图 | UI 单独给结论，不由预设验证推导 |
| 只有工具或界面、没有 Agent 预设 | 可以是普通插件；不出现在预设选择器 |
| 依赖 DSH 内部补丁、替换 DS Bot 生命周期 | 不支持 |
| 屏蔽协作必需工具或扩大 Bot 权限 | 不允许绑定 |

检测状态建议：待验证、可绑定、部分兼容、不兼容。另列安装状态、界面状态和是否需要重启；不将它们混为一个绿灯。

## 7. UI 与交互依据

遵循 `docs/design/ui-standard.md`；源文案英文，中文通过现有 i18n。以下为低保真流程候选，尚未通过 PROTOTYPE_REVIEW；不固定导航位置、布局和按钮。

```text
DS Bot → Plugins
  Discover：搜索/浏览 → 详情 → 安装前检查 → 用户安装
  Installed：插件版本、启用状态、预设、更新/卸载入口
  Compatibility：检查结果、证据、失败原因、重试

安装 → 等待加载或重启 → 发现预设 → 兼容验证
  → 可绑定：出现在新建 Bot 的预设选择器
  → 部分兼容/待验证/不兼容：展示限制及下一步
```

必需讨论的状态：加载、无结果、无预设、网络失败、安装失败、缺少依赖、需要重启、检测中、检测失败、插件更新后报告过期、预设被多个 Bot 使用。先确认上述流程，再做页面原型；本轮没有制作视觉原型。

### 已确认的 UI 结构

- 左侧栏新增「插件」入口。
- 插件页包含「发现」和「已安装」两个标签。
- 插件详情提供兼容性检测结果；安装后从详情进入检测结果。
- 发现页优先展示提供 Agent 预设的插件，同时允许查看其他插件。

低保真原型见 [`docs/prototypes/cross-module/plugin-presets.md`](../../prototypes/cross-module/plugin-presets.md)。原型只固化上述结构，不固化仍待确认的权限和失败处理。

### 下一轮 UI 确认清单（候选，不作为正式决定）

- 入口：侧栏独立「插件」页，还是「设置 → 插件」；现有 `settings.js` 没有 Plugins 页，需新增入口。推荐侧栏独立页，方便发现与浏览，管理细节留在同一页面。
- 信息结构：推荐「发现 / 已安装」两栏切换，检测报告在插件详情中独立成页，可从安装结果与预设选择处直达；避免把所有操作堆在检测总表。
- 展示范围：发现页显示全部 DSH 插件，还是仅显示提供预设的插件；推荐预设插件优先，普通插件可切换查看。前提是公开来源能提供足够元数据，不能假装有可靠分类。
- 首次安装路径：详情展示来源、版本、预设、检测结论；安装后按真实结果提示重启或继续验证。Chief 操作也回传同一报告，操作后不强行打断用户当前页面。
- 不兼容/未知：允许安装，但在安装或绑定前显示确认提示；不兼容预设不进入可绑定列表。
- 新建 Bot：推荐单选一个工作预设，默认 standard；旁边可查看来源和检测报告，无有效预设时提供去安装入口。
- 更新/卸载：先列受影响 Bot；保留配置与历史，提供显式改用 standard 的恢复操作；已确认首版不做已有 Bot 任意切换，因此不能暗中用“自动切换 standard”解决依赖失效。

群中继行为和检测状态文案已确认。公开接口与来源调查由 Agent 执行，不要求用户选择技术 API。仍需完成公开 API 核验，并确认安装来源、检测执行边界和最终验收后，才能确认整份文档。

### 群中继处理（已确认）

一个群聊在 DS Bot 中有一个只负责转发的群会话。它收到用户消息后调用 `group_relay`，再把任务交给被点名的成员；成员各自在自己的会话中工作并使用自己的预设。群中继本身不承担教学、写作等专业任务，因此建议继续使用受控的标准配置，只允许它执行转发所需的工具。若某个成员预设不能提供 `group_relay` 所需能力，检测报告应标记“可单聊，不可用于群聊”，而不是改变该成员的预设。

### 检测状态文案（已确认）

建议用“能力结论 + 下一步”，避免只显示颜色或笼统的“成功”。界面文案源语言仍为英文，中文为对应翻译：

| 状态 | 英文主标签 | 中文显示 | 说明/下一步 |
|---|---|---|---|
| 未检测 | Not checked | 尚未检测 | 开始检测 |
| 检测中 | Checking compatibility | 正在检测兼容性 | 保持当前页面，等待结果 |
| 可绑定 | Ready for Bot | 可用于 Bot | 可在新建 Bot 中选择 |
| 部分兼容 | Partially compatible | 部分兼容 | 显示可用能力与限制；可安装，按限制决定是否可绑定 |
| 仅单聊 | Single chat only | 仅支持单聊 | 可用于 Bot 单聊，不能加入需要群中继的群聊 |
| 待验证 | Needs verification | 需要人工确认 | 显示未知项；安装或绑定前弹出确认提示 |
| 不兼容 | Not compatible | 不兼容 | 允许安装，但不能绑定为 Bot 工作预设 |
| 检测失败 | Check failed | 检测失败 | 显示失败原因和重新检测 |
| 已过期 | Check outdated | 检测结果已过期 | 插件或 DSH 版本变化后重新检测 |

建议把“插件已安装”和“预设可绑定”分开显示。例如：`已安装 · 不兼容`，而不是把插件标成“安装失败”。

## 8. 安全边界

- 保护对象：团队、会话、记忆、工作文件、凭证、权限配置和用户原有 DSH 数据。
- 不可信输入：插件包、下载地址、元数据、预设说明、第三方代码和检测输出。
- 必要控制：沿用现有审批与权限；绑定预设不授予 Main Bot 身份；安装目标固定为当前应用 profile，不能由包元数据改写。
- 安装前仅检查可取得的声明和包内容，不能 import/执行目标代码后仍称为静态检查。安装器生命周期脚本是否执行，必须核对公开管理接口并向用户准确说明。
- 安装或加载插件可能运行代码。独立 profile、临时目录或子进程均不等于安全沙箱；不能承诺阻止文件或网络访问。
- 动态测试使用临时测试数据与 mock model，不使用用户数据或真实凭证。执行不可信插件前的授权方式、是否需要 OS 隔离仍待确认；不能把自动执行纳入既定范围。
- 检测报告不包含密钥、cookie 或原始 DSH_HOME 内容；按证据输出结论，不给“安全认证”。

可选加固（不纳入首版承诺）：OS 沙箱、签名信任目录、第三方审计系统。不新建通用 RBAC 或策略引擎。

## 9. 功能范围

### 包含（设计目标；首版边界待确认）

插件发现与管理入口（用户与 Chief 可操作）、预设枚举、兼容报告、新建 Bot 选择预设、会话接续保持选择，以及 StudyMate 实例验证计划。

### 不包含

不开发新的 Agent 运行时，不改 DSH。已有 Bot 任意切换不在首版，失效后显式恢复 standard 除外。不做专用 UI 通用适配，不提交远程 PR 或发布安装包。

### MVP 开发准入判断

已满足的产品条件：独立桌面版、插件发现/已安装页面、新建 Bot 选择预设、用户和 Chief 的操作路径、兼容提示、不兼容仍可安装、群成员各自预设、失效/卸载保留配置与历史、检测状态文案。

开始编码前只保留一个技术门槛：确认 DSH 公开 API 能覆盖插件列表/安装/卸载、预设枚举、带 `agentPreset` 创建 Session，以及独立桌面 profile 的重启或热加载行为。若某项公开 API 不存在，该项停止并记录为 DSH 上游缺口，不扩展设计绕过它。

## 10. 技术方案

优先复用 DSH 公开插件管理与 Agent 预设服务，不复制 DSH 私有实现。候选路径：

1. 复用公开插件管理页面或组件：成本较小，但需证明可挂入 Bot 导航及桌面 profile。
2. 若只有公开管理 API：在 Bot 中做薄界面，调用 API，保持同一安装源和配置。
3. 若所需公开接口不存在：记录 upstream 缺口并停止对应能力，不绕过到内部文件。

技术核验清单：插件目录、安装/更新/卸载、预设来源与稳定 ID、加载错误、依赖信息、有效工具集、客户端页面挂载、会话创建及提示词组合。当前只观察到 `agentPresets.list()`、创建时传 `agentPreset` 和可选 `pluginNavigation`，其他能力未获证明。

候选数据变更：Bot 增加预设标识，旧数据缺省维持原行为；标识的来源归属、防重名和版本关系在核验公开 API 后定。检测结果与插件版本、DSH 版本、检测规则版本关联；变化后旧报告失效。报告持久化方式待确定，不先建数据库或通用兼容性框架。

不能只检测提示词是否存在：需验证实际工具可调用、Main Bot 权限、审批、群聊交接及上下文接续。规则之间的语义冲突无法靠静态匹配穷尽。

## 13. 验收标准

以下作为待确认验收草案。

- 功能：安装提供多个预设的测试插件后，列出实际有效项；无预设插件不产生虚假选项。选定预设创建 Bot，检查实际 Session 配置一致。
- 连续性：换段、重启后预设不变；旧聊天可读；没有预设字段的旧 Bot 保持原行为。
- UI：无结果、失败、重试、重启提示可操作；更新导致的旧报告明确标记过期，不能继续据此绑定。
- 安全：普通 Bot 使用外部预设后调用主 Bot 专属操作仍被拒绝；审批不被绕过；测试不读写用户原有 DSH。
- 协作：私聊派任务、结果返回、群成员响应和群中继均有工具调用与结果证据；不能仅以模型口头声明通过。
- 错误：缺失/损坏预设、依赖缺失、版本不符显示明确原因；已绑定插件卸载前列出受影响 Bot；处理方式按确认后的规则执行。
- 实例：记录 StudyMate 的确切包版本、DSH 版本、环境；学习预设和阅读界面分别给通过/失败/未验证结论。

## 14. 测试计划

先做无第三方代码的测试夹具：有效预设、无预设、损坏预设、缺依赖、工具受限、同名来源及版本变化。mock model 验证团队工具、权限和接续；静态检查不能证明模型教学质量。

代码实现后在 ds-bot 下执行 `npm test`、`node scripts/build-client.mjs --check`、`npm run lint`；host/index 改动运行规定的 mock 冒烟并停止进程。profile 改动运行 app 对应测试。界面按 record-browser-gif 技能提供真实分支服务的证据；涉及真实模型的要求若与“测试只用 mock”冲突，先记录并解决，不接触用户凭证。

实际验证及证据见第 20 节。

## 15. 风险与回滚方式

风险：公开 API 不足、第三方全局配置和样式污染、工具视图缺失、预设压缩机制冲突、安装后页面无法启动。

候选回滚：保留旧会话及原预设配置；按公开管理能力禁用故障插件，用户明确选择后恢复 standard。插件造成的任意文件或配置副作用不能承诺自动回滚；需确认公开安装事务能力后界定恢复范围。

## 16. 复杂度控制

## 20. 最终实现与验收

### 实现范围

- 独立桌面版侧栏「插件」通过公开 `pluginNavigation.openList()` 打开 DSH 原生插件页；原生已安装、发现、社区插件市场标签保留各自页面和安装确认流程。DS Bot 通过公开 `plugins.tab` 扩展槽增加「Bot 预设」标签，提供检测、重新确认和显式恢复；新建 Bot 的预设选择保留。
- 默认安装并启用社区 DSH Markets（`dshmarket@1.73.11`），通过 DSH 公开市场服务查询目录。首次读取插件目录、且没有已有来源时，配置其推荐的 `https://cdn.jsdelivr.net/npm/dsh-plugin-catalog/index.json`；保留已有自定义来源，用户后续清空来源不会被自动补回。社区目录不称为官方目录。
- 发现页的搜索、分类、排序和版本详情沿用 DSH 原生行为，替代早期自建页面的预设关键词优先排序；兼容性仍由 Bot 预设检测说明，不从排序推断。
- 更新插件沿用 DSH 的卸载后重装流程，界面提供说明，不另造更新器。
- Chief 使用 `bot_plugins` 操作；普通 Bot 原有 DSH 权限保持不变，新增工具的变更动作只供 Main Bot。没有给插件操作增加新的逐次审批。
- 新建、群成员会话、换段和复制沿用 Bot 所选预设。插件形态不开放新入口。
- 预设缺失或损坏后不静默回退；显式恢复 standard，保留旧分段、Bot 配置和群成员历史。
- 内置核心 bundle 不能从新入口删除或停用。

### API 核验

使用锁定版本 `0.2.1-rc.5` npm 包公开 README、导出类型及真实服务核验：

| 服务 | 使用的公开能力 |
|---|---|
| `pluginManager` | `listBundles`、`inspect`、`installBundle`、`removeBundle`、`setBundleEnabled`，返回应用状态及重启要求 |
| `pluginMarket` | `listIndexes`、`setIndexes`、`search`；仅查询已配置来源 |
| `agentPresets` | `list`、`compositionInventory`，读取加载诊断和启用模块 |
| `sessionController` | 创建时传入 `agentPreset` |
| `@deepseek-ai/dsh/profile-boot` | 启动隔离的真实 DSH 测试服务 |

没有读取 DSH 安装内部文件作为产品依赖。新增一个 Host 服务封装和一个预设检测标签/选择器模块；Bot 状态增加预设标识和确认指纹。原生页面通过公开服务和扩展槽复用，不复制上游组件，不添加运行依赖。React/React DOM 仅新增为测试环境依赖，用于真实组件交互测试。

### 检测的实际边界

- 有效 standard 显示可用于 Bot。
- 不存在、损坏或启用已知 PTC 模块的预设显示不兼容，禁止绑定；插件本身仍允许通过 DSH 包管理器安装。
- 其他第三方工作流程保持「需要人工确认」，用户明确确认当前指纹后可创建 Bot，不冒称已全面验证。
- 指纹覆盖预设、组合、bundle 版本/启用状态与规则版本；发生变化时旧确认失效，要求复核。
- 「部分兼容」「仅支持单聊」等文案已保留，但没有足够证据时不为了显示状态而虚构检测结论。
- 公共预设目录没有直接提供所属 bundle；详情明确列的是当前环境中的预设，不猜测归属。
- 技术澄清：`group_relay` 属于群中继会话，不要求成员预设自带该工具。成员使用 DS Bot 注入的团队工具。前期描述混同了两者，实现没有因此误判成员缺少 relay 工具。

不建立插件安全扫描器、OS 沙箱、通用兼容规则框架或专用界面适配器。兼容报告不代表安全认证。
